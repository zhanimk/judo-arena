# Проверка и доработка турнирного движка

Дата: 26 октября 2026. Проверено рабочее дерево проекта на Node 22.22.1. Ни пользовательская БД, ни production-сервисы при испытаниях не изменялись.

## Как повторить

```bash
nvm use
npm run test:engine
npm run test:engine:db
```

Первая команда тестов запускает быстрые проверки сеток, судейских действий, таймеров, отмен и транзакций. Вторая требует работающий Docker: сама создаёт отдельные PostgreSQL и Redis на случайных loopback-портах, применяет все миграции, проводит турниры и удаляет контейнеры. `DATABASE_URL` основной базы не используется. До запуска должны быть установлены зависимости проекта.

Полная проверка проекта: `npm run verify:local`. Все DB-тесты отдельно запускаются через `npm run test:db -w api` только с явно заданными тестовыми `DATABASE_URL` и `REDIS_URL`. Browser E2E требует запущенные frontend/API с демо-аккаунтами на отдельной базе: `BASE_URL=... API_URL=... npm run test:e2e`.

## Исправленные дефекты

1. Посев двух спортсменов возвращал четыре слота: дробное число пар округлялось циклом вверх в каждой половине. Теперь возвращаются ровно два слота; добавлены проверки размера сетки, повторных ID и неконечных значений.
2. Попарная сортировка личных встреч была нетранзитивной при цикле из трёх побед. Теперь сначала формируются группы равных результатов, затем последовательно применяются критерии. Неразрешённая ничья сохраняет общее место (`tied=true`); ID задаёт только порядок отображения, а не спортивное преимущество.
3. RR и MIXED использовали разные расчёты, а frontend самостоятельно назначал порядковые места. Теперь оба формата используют общий расчёт; публичная сетка, кабинеты и отчёты отображают серверные места. До завершения группы и разрешения квалификационной ничьей спортсмен не отмечается как прошедший в плей-офф.
4. Завершённая группа с ничьей могла выглядеть как пустой источник плей-офф и отдать BYE сопернику. Теперь квалификационные слоты структурно зарезервированы даже после завершения матчей группы.
5. Финал MIXED передавался как очередной `main`-раунд и формировал ребро к несуществующему матчу. Продвижение из последнего раунда теперь отсутствует.
6. Финализация проверяла преимущественно готовые пары и могла пропустить незаполненный финал или другую допущенную категорию без сетки. Теперь проверяются все групповые таблицы, неразрешённые места, целевой финал и категории с допущенными участниками.
7. В обычном переходе статуса `IN_PROGRESS → COMPLETED` можно было обойти проверку результатов и начисление рейтинга. Этот переход теперь вызывает полноценную финализацию.
8. Проверка результатов и запись рейтинга выполнялись в разных снимках БД. Теперь чтение, проверки, рейтинг, статус и аудит финализации находятся в одной Serializable-транзакции. Исправление результата повторно проверяет статус турнира внутри своей транзакции.
9. Для отменённого/завершённого турнира добавлена проверка внутри транзакций старта, начисления оценок, удержания, ручного результата, подтверждения и технической победы. Отменённый матч также нельзя завершить технической победой.

10. Явно выбранный RR на 6–8 спортсменов раньше заменялся на SE. Теперь выбор сохраняется, а при 9+ возвращается понятная ошибка с предложением SE/MIXED. Автоматическая круговая система для 2–5 спортсменов сохранена.
11. Участник без указанного пола мог попасть в половую категорию, хотя возрастные данные проверялись строго. Теперь неизвестный пол исключается, как и несоответствующий возраст; статус взвешивания также проверен на реальном пути заявки → генерация.

## Решение секретаря при ничьей

На странице сетки администратор видит форму «Разрешение ничьей». Кнопками можно менять только порядок внутри одинаковых неразрешённых мест. Нужно указать основание: например, решение главного судьи или зафиксированную жеребьёвку. Обычные пользователи видят сообщение об ожидании решения.

API: `POST /api/brackets/:id/standings/decision`, только администратор. Нужны `section`, полный порядок спортсменов группы `order`, `reason` и актуальный `fingerprint` из ответа сетки. Повторные/чужие участники и перестановка уже доказанных мест отклоняются. Причина, автор и порядок фиксируются атомарно в журнале.

Решение привязано к версиям и результатам матчей. После сброса/исправления оно становится недействительным; система не переиспользует прежний жребий автоматически. После начала реальных матчей плей-офф порядок нельзя тихо заменить: требуется явный сброс/исправление группового матча с откатом зависимой ветви.

Для MIXED обязательного решения требуют ничьи, затрагивающие первые два места. Равные места остальных спортсменов могут остаться общими. Для финальных RR-мест требуется разрешить все оставшиеся ничьи.

Сохранена действующая система дополнительных показателей проекта: ippon, waza-ari, разница очков. Её соответствие регламенту конкретного соревнования должен подтвердить организатор; универсальным утверждением всех правил IJF этот код не является.

## Результаты и пределы

- `npm run verify:local`: успешно, **616 API-тестов**, линтеры, обе обычные сборки, frontend TypeScript; JS **2496 KB**, лимит 3000 KB.
- Весь DB-набор: **82/82**, включая 30 новых сервисных сценариев движка.
- `npm run test:engine`: **394/394** быстрых целевых проверки.
- `npm run test:engine:db`: **43/43** на самостоятельно созданной пустой PostgreSQL и Redis; все 33 миграции, автоматическая очистка контейнеров.
- Browser E2E: **48/48**, включая новый сценарий решения ничьей через интерфейс.
- Чистые модули `bracket-engine`: **99,21% строк**, **95,74% ветвей**. Покрытие всего включённого в проверку набора API: **93,08% строк**, **87,26% ветвей**, **96,89% функций**. Процент относится только к перечню `include` в `api/vitest.config.ts`, а не ко всему backend.
- `npm run build:vps` и контроль размера Node SSR frontend: успешно на окончательном коде.

Выполнено 511 полных симуляций сеток (381 SE, 123 MIXED, 7 RR), дополнительно проверены посев по клубам и перестановки циклической ничьей.

Автономное судейство без сервера и несколько одновременно работающих API по-прежнему не поддерживаются как проверенный режим. Восстановление удержания проверено на настоящей БД, но это не испытание аварии конкретного VPS или электропитания площадки. Внешние оплаты, email и S3 не входят в тест движка.
